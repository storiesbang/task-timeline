# 建議優先順序

2026-10-17 加入（commit `0be2452`），已部署到 M1 與 tasks.storiesbang.com。

## 需求

很多階段同時進行時，顯示「建議先完成哪一個」。參考資料是使用者自己整理的各種優先度框架（艾森豪、MoSCoW、ICE、RICE、WSJF、EDD、LLF、CR、SPT、複合公式）。

## 討論過、沒採用的方案

- **讓使用者自選法則**：ICE、RICE、WSJF、艾森豪都要替每個階段打好幾個分數，建階段的成本變高，最後可能沒人填。
- **多個法則取多數決**：各法則看的是不同東西，多數決的結果說不出「為什麼排第一」。時間類法則（EDD／LLF／CR／SPT）用同一組輸入，投出來的結果大多一樣。
- **SPT**：CR 已經把剩餘工作量算進去，再加會重複。

## 採用：融合三個法則

實作在 `lib/timeline.ts` 的 `priorities()`、`crStatus()`，測試在 `lib/timeline.test.mjs`。

```
剩餘工作量 = max(1 小時, 階段長度 × 未完成待辦比例)   沒有待辦就當比例 = 1
CR        = (截止 − 現在) ÷ 剩餘工作量                  臨界比，緊急度＋進度
權重       = 重要度係數 × (1 + 0.2 × 同專案後面未完成的階段數)
分數       = CR ≥ 0 ? CR ÷ 權重 : CR × 權重               越小越先做，逾期的一律排最前
```

- 重要度係數：低 0.6、中 1（預設）、高 1.6。取自 WSJF 的價值項。
- 阻塞權重取自複合公式的 Downstream Blocks。「後面」的意思是開始時間 ≥ 這個階段的截止時間。
- 時間點階段長度是 0，靠「至少 1 小時」避免除以 0。
- 這些係數都是初始值，還沒依實際使用的情況調整過。

### CR 標示（`crStatus`）

| CR | 標示 | 意思 |
|---|---|---|
| < 0 | 已逾期 | 截止時間已經過了 |
| 0～1 | 落後 | 照原本排的時間估算，剩下的時間不夠做完 |
| 1～1.5 | 緊繃 | 幾乎沒有緩衝 |
| ≥ 1.5 | 不標示 | 時間還算充裕 |

前提是「排 N 天＝估計要做 N 天」，而且每個待辦的份量差不多。

## 畫面

- 工具列下方的「建議優先」列出前 3 名，附上逾期／落後／緊繃標示。點一下會開啟階段編輯。沒有待辦的階段旁邊會顯示「?」。
- 時間軸上，前 3 名的階段條會有 ①②③ 編號。只標前 3 名，避免時間軸太雜。
- 階段編輯視窗新增「重要度」欄位（低／中／高）。`Phase.importance?: 1 | 2 | 3`，舊存檔沒有這個欄位時當作「中」。

## 已知限制與待辦

- **沒有待辦的階段會被估得比較悲觀**：只要進行超過一半，就會被標成「落後」。使用者說自己的階段多半沒寫待辦，原因只是懶得寫。
- **還沒做**：建立階段時強制至少寫 3 個待辦。使用者提過這個想法，先擱著，如果悲觀標示太煩人再加。
- 係數（0.6／1／1.6、0.2）要依實際使用的感受再調整。
